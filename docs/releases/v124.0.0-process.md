# Receiz v124.0.0 Release Process — Reality Becomes Infrastructure

**The Production Runtime for Verified Civilization.** The process advances coordinated release identity without allowing package metadata, a server, a database, a session, or release prose to outrank the sealed proof object.

## Goal

Release one coordinated V124 production runtime in which sealed proof objects and exact authenticated heads remain authority while durable coordination, private access, exactly-once execution, and atomic multi-domain progression become deployable universal infrastructure.

## What Worked

- Binding every runtime response to authenticated proof/head evidence preserved the existing authority hierarchy.
- Coordinating package, registry, migration, documentation, and release identities exposed stale promotion surfaces before release.
- Keeping production mutations separate from repository evidence prevented local implementation from becoming a deployment claim.

## Order

1. Freeze the exact V124 registry and predecessor digest without changing historical V123 bytes.
2. Lock `@receiz/sdk`, `@receiz/mcp-server`, `@receiz/ai-skills`, the constitutional verifier, root, lockfile, current registry, and compatibility matrix to `124.0.0`.
3. Generate current AI Skills, MCP metadata, OpenAPI, and Receiz Docs projections from their repository sources.
4. Run local adversarial, type, OpenAPI, docs/archive, AI, MCP, package, and release-lock checks.
5. Review the diff for authority downgrade, consumer-specific admission, external-operation overclaim, and historical-byte drift.
6. Commit the coherent repository candidate.
7. Separately perform and record package publication, migration application, deployment, production smoke, scale, adoption, Git tag, and signed attestation operations when authorized.

Durable proof memory remains first admission only, then append forever. A release tag or published package identifies bytes; neither becomes proof-object authority.

## What Did Not Work

- Promoting V124 product labels before advancing every release-law expectation left deterministic-surface contracts stale.
- Creating release authority documents without the canonical headings and path references left the release lock unable to verify their evidence chain.
- Relative links alone preserved navigation but did not preserve the exact repository coordinates required by the release ledger.

## Stop conditions

Stop on any forged transport acceptance, unauthenticated committed outcome, partial multi-domain write, private-access leak, recipient enumeration, stale session acceptance, V123 schema reinterpretation, unknown discriminator reaching callbacks, silently inoperative dependency, historical-byte change, or external evidence claim without an artifact.

## Practical Rule For Future Work

Promote runtime identity, public release labels, authority documents, canonical repository paths, generated projections, and their contracts as one bounded change. Keep navigation links working, keep repository coordinates explicit, and never infer an external release operation from local source state.
