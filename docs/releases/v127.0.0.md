**Proof Creation Runs Locally. Intelligence Runs Locally.**

Receiz v127 brings proof creation and intelligence to the device that holds the source. Builders can create and verify canonical sealed files locally through the SDK, MCP and AI workflows after one-time online signer enrollment. Receiz Mind combines local observation, sealed memory, portable identity and a bundled local model in its independently released web/PWA and macOS product. Exact artifact bytes and verified carried history remain authority above servers, sessions, SDK reports, MCP output and generated answers.

**The proof object is the application. One object, unlimited experiences.** V127 extends that v126 foundation into local creation and local intelligence: people retain the source, builders receive the canonical creation machinery, and intelligence reads evidence without becoming its authority. Identity, memory, ownership, Settlement and public witness continue through the same proof-native artifact system.

## Release outcomes

- **Create proof where the source lives.** The developer distribution packages the canonical sealer, durable device signer custody, proof resources and verification. After explicit enrollment and resource installation, sealing continues across process restarts without server signing or remote verification.
- **Run intelligence beside verified memory.** Receiz Mind records local observations, exports sealed PNG Memory Crystals, inspects exact source and answers through its bundled local model. Generated answers remain interpretations grounded in evidence; they cannot rewrite the memory they read.
- **Carry continuity between experiences.** Identity Seal/Record admission, multiple retained identities and explicit owner-scoped sync connect desktop, web and PWA while preserving the identity and enclosing proof objects. Connected web questions can use the running Mac's local model; that remote access path requires connectivity to the Mac.
- **Keep the whole object through recovery and publication.** Complete Showcase proof images, material originals, carried attachments, account history and public economy history survive their export, restore and transport paths. A failed transport cannot revoke held proof.
- **Make scale serve existing truth.** Retained memory heads, owner indexes, source checkpoints, bounded inspection and reduced backing-coordinate transport make complete held history usable without rebuilding it from partial pages. New verified history appends; settled first paint remains present.
- **Preserve lawful economic continuity.** Settlement projects from published proof and retained local events; signed subscription terms retain owner binding and their Kai interval. A notification, model response or device signing certificate creates no ownership, entitlement or Settlement authority.

## Offline SDK, MCP and AI workflows

The SDK ships the existing canonical file sealing core, the exact document proof WASM and proving key, explicit one-time canonical device enrollment, durable local signer custody, local proof generation, and canonical output verification. Node hosts use `@receiz/sdk/offline/node`; browsers use `@receiz/sdk/offline` with IndexedDB custody and installed offline resources. No server signing or remote verification occurs during offline seal calls.

Default MCP tools now cover enrollment, readiness, local file sealing, full KaiSigil coordinate generation and complete artifact verification without a developer-written sealer resolver. Files stay within the configured workspace and new outputs cannot overwrite existing files. AI skills carry the actual supported commands. The HTTP `assets.createProofObject()` operation retains its existing behavior; the offline entry point is explicit.

Full temporal authority uses the existing KaiSigil BLAKE3, Poseidon and Groth16 proof primitive. The distribution supplies its canonical circuit and proving key locally. Caller-supplied pulse and timestamp overrides are rejected; consumers verify exact coordinates, public signals and causal proof-head continuity. A sealed inner payload does not establish a claimed temporal history by itself.

The SDK also ships a durable local V120 subject host, composed with admitted Identity Record and enclosing artifact proof. It executes subject history, proof-brain retrieval, Twin streams, mandates and world transactions through the existing authority predicates. Each new temporal transition consumes a complete verified KaiSigil coordinate; exact source bytes and causal evidence survive restart. Portable export carries the original sealed sources, exact snapshot and complete temporal evidence. Sealed import verifies those sources and bindings before admission. Historical snapshots retain their original protocol and are explicitly not retroactively proved. See the [local subject execution guide](../../packages/receiz-sdk/docs/local-subject-runtime.md).

The current inventory contains 425 SDK client methods, 678 public functions and 330 MCP tools, with execution requirements carried into the AI distribution. Historical HTTP contracts remain explicitly classified: 69 newly mapped bindings and three older methods require an explicitly configured compatibility host. They do not point at absent default production routes. Offline sealing and the local subject host require no such host. Card checkout creates a session, not completed payment; a wallet read cannot execute Settlement. See the [HTTP execution boundaries](../../packages/receiz-sdk/docs/historical-http.md).

Canonical enrollment is online once. It obtains a certificate for a device-generated key. The distribution carries public verification roots and canonical proof resources; the device private key stays in local custody, and neither a root private key nor server credentials ship. A signature certificate does not create a Receiz ID, another person's ownership, transfer authority or Settlement permission. See the [offline sealing execution guide](../../packages/receiz-sdk/docs/offline-sealing.md) for Node, browser and MCP setup.

## Why it matters

**Creation, memory and intelligence can operate from held reality.** A developer can seal a file on the machine that holds it, save the exact artifact and verify it after reopening. A person can retain sealed observations, inspect their source and ask a local model about that evidence. Export, restart, a new reader or a temporary transport outage does not authorize replacing the proof object's history.

That is Reality-Grade Infrastructure in use: the object carries continuity; computation works on the device; applications and agents remain accountable to the source. Network services distribute, discover and append verified additions. They do not make already-held truth exist.
