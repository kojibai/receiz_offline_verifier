# Receiz v124.0.0 Regression Lessons — Reality Becomes Infrastructure

**The Production Runtime for Verified Civilization.** The strongest lesson is exact: a typed client, HTTPS response, durable database row, or SDK-shaped object cannot authenticate itself against the sealed proof object and exact head.

## What Regressed

The V124 release audit found promotion drift in repository contracts: deterministic-surface expectations still required V123 after the protected product surfaces advanced to V124, and release authority documents lacked the canonical headings and repository paths required by the release lock.

## Why It Regressed

Runtime and visible release identity advanced before every release-law projection advanced with them. Working relative links and accurate prose were present, but exact machine-verifiable repository coordinates and frozen section names were not promoted in the same bounded change.

## Locked Rules

- Arbitrary `baseUrl` responses and forged committed outcomes must fail before application callbacks.
- A payload self-hash is not admission when an enclosing proof object carries the stronger boundary.
- A stored plan must be independently resolved and rebound before execution; caller-restated plan fields are not custody.
- Idempotency means lookup-before-retry and exact committed/zero-write/unknown classification.
- Private access is filtered before hydration, not after coordinates reach the client.
- Capability presence is not operational capability evidence.
- V123 whole-pulse fields cannot be silently reinterpreted as micro-pulses.
- Supabase or any hosted store is sync and recovery beneath proof storage and continuity authority.
- Consumer-specific admission or branding would fragment a universal primitive and is forbidden.

The coordinated `@receiz/sdk` release preserves durable proof memory as first admission only, then append forever. These lessons are local release contracts; they do not claim publication, migration, deployment, production smoke, scale, or adoption.

## Contract Gates

- `pnpm release:lock` must verify V124 authority-document headings, working in-directory links, canonical repository paths, and every coordinated public release surface.
- `pnpm test:deterministic-surfaces` must require `v124.0.0` on the protected documentation-linked product surfaces without changing those surfaces.
- `pnpm test:release-freeze` must retain both gates so release promotion drift cannot pass as a coherent candidate.
