# Receiz v122.0.0 Regression Lessons

The proof object is authority. `@receiz/sdk` must verify the enclosing object before subject projection; private plaintext must remain at the edge; exact outcome lookup must precede retry; Phi must name Settlement or Reserve; and the database must remain recovery beneath held proof.

The settled Receiz application UX and deterministic first paint remain unchanged. Durable proof memory is first admission only, then append forever.

## What Regressed

Release preparation initially left current-version documentation, service-worker identity, historical sparse fixtures, and new lint boundaries out of sync. Value intents also required explicit execution binding so an unvalidated row could not be mistaken for Settlement or Reserve authority.

## Why It Regressed

The coordinated package surface advanced before every repository-wide release contract had been exercised from a full release worktree. The v122 work therefore had to bind current package truth, historical compatibility, production append behavior, and release evidence together.

## Locked Rules

- The enclosing proof object remains authority; a payload hash, database row, receipt, or API response cannot replace it.
- Private plaintext stays at the edge. Only public exterior data and encrypted recipient envelopes cross the global event boundary.
- Unknown execution outcomes are looked up before any retry or replan.
- Phi moves through exactly one named rail, Settlement or Reserve; USD is deterministic display only.
- Deterministic first paint and settled Receiz application UX do not change for developer API work.

## Contract Gates

The v122 release lock, SDK/MCP/AI package suites, transaction and migration contracts, security and value-loop gates, full release freeze, governance evidence, package dogfood, production migration verification, and production smoke checks are all required. A failed gate remains a release blocker.
