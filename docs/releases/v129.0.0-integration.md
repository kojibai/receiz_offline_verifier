## Card funding and purchase continuation

An authorized external app can call `client.connect.checkout` with the acting user's delegated grant and the calculated funding shortfall. The server binds the receiving wallet to that grant's account and application. `receiz:payments.create` permits checkout creation; `receiz:payments.read` permits `client.connect.checkoutSession` inspection. The full MCP adapters compose those same SDK methods; the restricted ChatGPT plugin excludes them.

After the user completes card checkout, inspect the actual session. A verified paid session runs the existing idempotent wallet settlement and returns the credited account and amount, including whether settlement was already processed. Check that evidence and the resulting wallet state before resuming purchase review/approval, payment and exact bearer delivery/claim. A redirect, an unpaid session or a checkout credential does not prove wallet credit or ownership transfer. The live insufficient-funds, reload/retry and separate-account acceptance stages remain recorded independently in [Conformance](v129.0.0-conformance.md).

Use the exact ID returned by Receiz registration for `RECEIZ_APPLICATION_ID`. Registered IDs are `rc_` plus 24 base64url characters. Existing native slugs remain valid syntax; syntax alone never authorizes an unregistered application. Do not lowercase, strip prefixes, use a username, or substitute `wildz`. `RECEIZ_CLIENT_ID` is the registered application coordinate; a Receiz ID is the subject's identity; a client secret belongs only on the server.

```ts
import { createReceizClient } from "@receiz/sdk";

const client = createReceizClient({
  baseUrl: "https://receiz.com",
  applicationId: registeredClientId, // exact server-supplied public coordinate
  accessToken: shortLivedAccessToken,
});
```

The [registered native session example](../../ai-skills/receiz-proof-authority/examples/registered-native-session.md) follows the real methods. Use the canonical signed challenge, explicit consent and genuine device-held identity proof; verify the stronger enclosing artifact before projecting its subpayload. Qualify the actual operations/dependencies, publish their sealed source and open the exact challenge-bound session. Tokens and sessions constrain execution; they do not become identity or source authority.

## Financial evidence is staged

Funding a wallet, confirming a payment and transferring a bearer asset are separate implemented routes with separate evidence. Check actual credited funds after hosted checkout. Review the fresh quote and approve the asset payment through its actual source-bound route. Verify exact delivered bearer bytes, then claim and use the actual asset; reconcile buyer custody and seller proceeds with the receipts.

The application-runtime wallet-first proposal currently returns `wallet_settlement_execution_required` when wallet execution must be supplied. It does not debit proposed funds or start a card call for that unexecuted debit. Compose the existing Settlement/Reserve/payment primitive required by the application. A prepared plan, a successful checkout or method presence cannot certify a purchase, delivered ownership, or asset use.

Concurrent buyers, unavailable/stale reservations, repeated approvals, reloads and lost responses require their actual retry/idempotency contracts. Reject unusable reservations before payment where the purchase route requires them. Preserve the enclosing sealed source through every stage; transport, subpayload hashes and application coordinates never replace it.
