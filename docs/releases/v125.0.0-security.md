# Receiz v125.0.0 Security and Authority Boundary

V125 security begins at the existing proof-object boundary. It does not add a verifier above the canonical verifier or create a new institution of trust.

## Admission order

1. Verify the enclosing sealed artifact and its canonical proof.
2. Verify its proof-bearing KKS/KaiSigil coordinate and exact prior head when temporal authority is required.
3. Parse the embedded payload only after the stronger artifact succeeds.
4. Verify the authorized grantor, actor proof, subject, custody, content, evidence, law, lifecycle, and causal coordinates required by that payload.
5. Project or append the admitted result beneath the object.

Runtime custody brands do not survive JSON, database, worker, RPC, MCP, or process transport. Exact bytes must be reopened and reverified across every authority boundary.

## Closed attack paths

- Self-authored issuer/evaluator/approver grants cannot authorize copied domains.
- Arbitrary digest-shaped evidence cannot satisfy an application minimum.
- A holder of someone else's subject artifact and role grant cannot manufacture attestation events without fresh actor proof.
- A future or retrocausal claim set, evidence bundle, supplemental bundle, event, or issuance cannot enter a lawful history.
- Post-deadline workflow events fail except the deterministic expiry append.
- Later grant revocation blocks later use without erasing valid earlier history.
- Renewal/replacement cannot create an independently current successor detached from the predecessor lifecycle append.
- A bare pulse number, Chronos-derived legacy value, repeated clock sample, or backward clock movement cannot become a new authoritative KKS append.
- Presentation text or a filename cannot impersonate an Identity Record/Seal.
- Non-2xx lawful-action responses cannot be interpreted as successful SDK or MCP calls.

## Storage and transport

The SQL statements below describe the original September 4 hosted implementation. The [September 5 rollback record](v125.0.0-operational-update-2026-09-05.md) supersedes them for current production behavior. Source-authority restoration review remains in progress; removed database routines cannot be claimed as current enforcement. Enclosing proof verification remains the stronger boundary.

- Law, admission, value, membership, and KKS append tables are private, RLS-enabled where applicable, and mutated through scoped service boundaries.
- Stable identities are locked; expected heads are compared; invalid, stale, duplicate, or conflicting operations write zero.
- The original hosted database functions independently recomputed proof-native value.
- OIDC scopes separate law registration, action admission, and value advancement; application identity reaches the registered-origin CORS boundary.
- HTTP parsing uses closed keys, canonical encodings, bounded files and MIME types, and explicit decoded-size ceilings.
- MCP uses opaque trusted-host references and confirmation. It does not place sealed artifact bytes, private keys, bearers, or authority material in model context.
- Sender and receiver reopen and verify the same sealed committed transition. Server/database synchronization cannot convert a candidate or self-hashable receipt into Settlement.

## Authority exclusions

Database rows, session state, server responses, storage paths, access tokens, model output, MCP success framing, AI prose, OpenAPI text, chain anchors, institutional identity, and government recognition are mechanics or representations. None is proof authority.

## Disclosure and evidence boundary

The public Reality Grade Infrastructure repository is an allowlisted, digest-manifested projection of SDK, MCP, AI Skills, public doctrine, governance, conformance, and release evidence. It excludes the private application, secrets, production data, internal migrations, and operational material. Public issues are for correctness and interoperability; suspected vulnerabilities use private GitHub Security Advisories.

Exact remaining evidence boundaries are recorded in [evidence status](v125.0.0-evidence-status.md). An unpublished tag, unsigned attestation, unverified Docs route, or unrun authenticated mutation smoke is named as such; none is filled with inference.
