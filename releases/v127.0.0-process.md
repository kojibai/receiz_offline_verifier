# Receiz v127.0.0 Release Process

## Goal

Ship the implemented offline sealing primitive through SDK, MCP and AI skills; include the entire post-v126 history and Receiz Mind in the official coordinated release.

## What Worked

Reuse of the canonical seal core and production pinned verifier produced real disconnected artifacts across eight carrier classes. Local device enrollment stayed separate from root authority.

## What Did Not Work

The first integration called the low-level verifier without its existing pinned-root context and correctly failed closed. Correct composition supplies the existing SDK pinned roots, without changing the verifier. An incomplete PDF test input was replaced with a structurally valid fixture.

## Practical Rule For Future Work

Verify actual packed entry points, persisted custody and exact output bytes. Do not describe an unresolved adapter hook as a complete developer workflow. Record blockers honestly before tagging or publishing.

## Publication sequence

Complete local implementation, package qualification and the full release gate before committing the v127 candidate. The package maintainer then publishes the coordinated packages from that commit in dependency order: `pnpm ai-skills:publish`, then `pnpm sdk:publish`, then `pnpm mcp:publish`. Each command retains its repository release checks. Publication of one package alone does not establish a complete installable distribution.

After all three npm publications, verify registry versions and a clean external installation of the exact published packages. Then complete the official release, release attestation and application/Academy documentation delivery with their deployment checks. Keep the release candidate status until those boundaries are verified; local packed execution does not prove registry publication or deployed behavior.

The `@receiz/sdk` v127.0.0 continuity contract remains **first admission only, then append forever**: reuse admitted proof immediately, and accept only verified additions behind the held head.
