# Receiz v113.5.0 Release Process

The public package surface is `@receiz/sdk`. Durable proof memory remains **first admission only, then append forever**.

## Goal

The functional release range is exactly `v113.0.0..0c68fe4aa1bdd04e1f8161642778ad427dccb9e9`. Release preparation may change version metadata, release labels, release contracts, release records, generated package output, and lint-only dead bindings. It may not change product logic.

PR #223 and its v114 branch are excluded.

## What Worked

1. Record the untouched `main` lint baseline.
2. Remove all lint warnings without changing runtime branches, data flow, authority, or visible behavior.
3. Coordinate app, `@receiz/sdk`, `@receiz/mcp-server`, `@receiz/ai-skills`, and verifier package versions at `113.5.0`.
4. Preserve v113.0.0 ruleset, registry, artifact law, compiler target, operation matrix, and compatibility range.
5. Write release notes from the exact Git range and net code state.
6. Run lint, focused release contracts, coordinated packed-package qualification, governance controls, and full `pnpm test:release-freeze`.
7. Inspect Git diff and visual evidence before commit, tag, push, package publication, or GitHub release publication.
8. Generate and verify the signed attestation from the committed release tree after the configured approval and Ed25519 signing values are present.

## What Did Not Work

The first release-lock checkpoint found one intentionally unused test fixture without the repository’s underscore marker and release records that lacked the generic lock’s exact canonical heading/path strings. Those release-only issues were corrected without changing product logic or authority.

Fresh browser evidence then exposed a pre-v113 inline-label layout defect in the standalone Offline Studio. Adding `display: block` restored the complete Seal and Verify file-drop targets without changing proof logic, and the frozen offline invariant now requires that layout boundary.

Signed attestation remains blocked until the configured release approval and managed Ed25519 signing variables contain values. No approval identity or signing material may be invented.

## Practical Rule For Future Work

Tagging, pushing, GitHub release publication, package publication, deployment, and production mutation remain explicit release actions. GitHub mechanics may publish evidence; they do not become proof authority above the repository’s sealed artifacts and release contracts.
