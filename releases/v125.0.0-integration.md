# Receiz v125.0.0 Any-Architecture Integration

Transport choice is mechanics. The authority sequence is invariant:

> source → evidence → relationship → permissible inference → representation

Use the package-root exports from `@receiz/sdk@125.0.0`. Use `@receiz/mcp-server@125.0.0` when an agent host needs opaque-reference tools. Use `@receiz/ai-skills@125.0.0` to bind an agent's operating procedure to the same laws.

## Baseline integration

1. Retain the exact source and enclosing sealed proof object.
2. Verify the object with the canonical verifier before reading authority-bearing embedded payloads.
3. Verify any authoritative Kai coordinate through the proof-bearing KKS/KaiSigil boundary.
4. Admit the verified object into durable local proof memory once.
5. Bind every later append to the exact previous head and a strictly advancing lawful coordinate.
6. Paint known verified truth immediately; synchronize only verified additions.
7. Reopen and reverify exact bytes when crossing a process, persistence, HTTP, MCP, or device boundary.

## Attestation and credential integration

Create the v125 attestation authority from the supported package root. Bind domain roles to an authorized grantor. Require fresh Receiz ID/PBI actor proof over every event and prior head. Open referenced evidence artifacts before counting them. Enforce material causality, deadlines, evaluation, approvals, issuance, prospective revocation, and lifecycle-head binding through the exported reducers and verifiers.

Do not authorize a role from a self-hashable application namespace. Do not accept an evidence digest without its sealed proof object. Do not infer event authorship from possession of a grant.

## Lawful-action and value integration

Use `createReceizV125LawfulActionClient` for the hosted HTTP boundary or the framework-neutral v125 functions for same-runtime verification and planning.

The `125.0.0` package APIs below are published. The [September 5 production SQL rollback](v125.0.0-operational-update-2026-09-05.md) removed routines used by the hosted registration, admission and value-head adapter. This guide does not establish current hosted execution availability or source-authority restoration. Framework-neutral enclosing-source verification and deterministic value primitives remain implemented; later local-source integration work is not claimed as part of the published package bytes.

1. Create and seal a current-registry lawful-action law proof object.
2. `registerLaw({ proofObject, idempotencyKey })` with `receiz:lawful-actions.laws.write`.
3. Verify the completed `receiz.portable-execution-authority.v124` transition locally; derive causal claims and Kai coordinates from it; seal the lawful-action proof object.
4. `admit({ lawDigest, proofObject, expectedPriorAdmissionDigest, idempotencyKey })` with `receiz:lawful-actions.write`.
5. `deriveValueHead({ membershipId, expectedPriorValueHeadDigest })` with `receiz:lawful-actions.value.write`. Do not submit an amount or valuation coordinate.
6. Plan the sender and receiver transition with `client.value.edge.planSettlement(...)` or `planReserve(...)`.
7. Seal and commit both transition members in SDK-custodied edge stores; create portable committed recovery; optionally publish it for additive global synchronization.
8. Confirm at the sender edge and accept at the receiver edge. Every call reverifies the portable sealed transition.

```ts
const transfer = await client.value.edge.planSettlement({
  applicationId,
  amountPhiMicro,
  sourceProofObjectId,
  sourceValueHead,
  destinationSubjectId,
  expectedDestinationHead,
  usdPerPhiMicrocents,
  priceBasis,
  idempotencyKey,
  attemptId,
});

const verifiedSet = await client.value.edge.verifyTransitionSet(transitionSet, {
  audience: applicationId,
});
const prepared = await client.value.edge.prepareCommitSet(verifiedSet);
const committedTransitions = await commitAtSenderAndReceiverEdges({
  verifiedSet,
  prepared,
  localStores,
});
const recovery = await client.value.edge.createRecovery({
  applicationId,
  transitionSet,
  committedTransitions,
});

void publishForAdditiveGlobalSync(recovery);

await client.value.edge.confirmSettlementSend(recovery, {
  applicationId,
  participantId: transfer.sourceParticipantId,
});
await receiverClient.value.edge.receiveSettlement(recovery, {
  applicationId,
  participantId: transfer.destinationParticipantId,
});
```

## Architecture mapping

- **Browser/device-local:** verify, retain, and paint proof locally; delegate only additive synchronization.
- **Node/serverless/database:** reverify exact bytes at entry; use persistence for availability, indexing, and CAS—not authority.
- **MCP/agent:** keep proof bytes in trusted-host custody; expose only opaque references and require confirmation for mutation.
- **Game/World:** bind the governing action law to the completed deterministic subject/world transition; derive heads, commitments, witness, and Kai rather than accepting independent claims.
- **Chain-anchored:** publish digests or availability as mechanics; chain presence cannot replace enclosing proof verification.
- **Institution/government:** apply the same law, scopes, proof verification, evidence, custody, and deterministic projection as every other reader.

No adapter may introduce a second verifier, new authority token, or server-confirmation layer above the canonical proof object.
