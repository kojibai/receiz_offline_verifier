# Receiz v115.0.0 Regression Lessons

The public package is `@receiz/sdk`. Durable proof memory remains
**first admission only, then append forever**.

## What Regressed

Earlier iterations exposed four release risks:

- a corrupt shared-app PBI outbox could be normalized to empty and overwritten
- an active flush could leave proofs admitted during that flush pending
- permissive VM evidence could overstate browser-owned signing qualification
- the promoted current registry verifier still expected v114 directly after
  v113

## Why It Regressed

The paths were reviewed in isolation. Standalone Studio and shared app outbox
parsers did not initially enforce the same fail-closed contract. Flush
completion meant “processed the initial snapshot,” not “reached bounded
quiescence.” Synthetic credential helpers exercised algorithm shape but not
the actual browser custody boundary. Current-version promotion updated the
registry constant before every consumer of the predecessor chain.

## Locked Rules

- Corrupt durable proof state is contradictory evidence, never empty state.
- Active flush owns a bounded quiescence loop and coalesces overlapping callers.
- Real browser-created proof successors independently qualify synthetic vectors.
- Current registry verification names v115 and requires the immutable v114
  digest as predecessor.
- Frozen v114 proof schemas and verifiers remain historical authority; v115 is
  additive.

## Release-Lock Requirement

This record is mandatory release evidence. Corrupt durable proof state cannot
be normalized to empty state, active flush cannot strand same-run admissions,
synthetic credentials cannot be promoted to physical-device evidence, and a
current registry verifier cannot skip or rewrite its immutable predecessor.
