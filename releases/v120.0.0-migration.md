# Receiz v120.0.0 Migration

Developer surface: `@receiz/sdk@120.0.0`. Historical sealed proof objects require no rewrite. Applications adopting living-subject execution must migrate their current runtime mechanics as one coordinated v120 boundary.

## Compatibility class

- Exact historical proof artifacts remain readable, verifiable, exportable, and appendable under their carried law.
- Historical runtime admissions, capabilities, plans, mandates, jobs, receipts, or snapshots do not authorize a v120 transition.
- Application, SDK, MCP, AI Skills, schemas, registry, operation matrix, and reducer must be coordinated at `120.0.0` before a living-subject write.
- No migration step may replace sealed artifact truth, exact subject history, unknown namespaces, or deterministic first paint with a database, server, model, index, receipt, or latest snapshot.

## Required application migration

1. Upgrade `@receiz/sdk`, `@receiz/mcp-server`, and `@receiz/ai-skills` together to exact `120.0.0`; bind registry digest `0728651789b26e1d10c1991ec1c06c1ea4a576f0c6520537b250b171f8857073` and operation-matrix digest `1c779ee5ade4b877ae9c6922ab02ba96fffffeb7580f1cf105a59fbb4424f351`.
2. Represent each creature, character, vehicle, agent, or collectible as `receiz.subject.v1` with immutable identity and the complete byte-preserved namespace map.
3. Replace person-Twin multiplexing through `threadKey` with `receiz.subjects.twin.*`. A thread key may remain a conversation subdivision beneath the subject; it cannot be subject identity.
4. Admit every existing complete primary proof object into the subject proof brain at the exact current head. Preserve full long-form text and exact bytes. Do not import a 96-object prompt, summary, embedding, or latest database snapshot as canonical history.
5. Replace loose autonomous `jobs.enqueue({ kind, payload })` work with an owner-confirmed `receiz.subject.mandate.v1` plus `receiz.subjects.runtime.enqueueTick` using exact subject, world, and mandate heads.
6. Route every consequential action through `world.planCommand`, `validateCommand`, and `executeCommand`. Model speech and structured intentions remain proposals.
7. Route every relationship, battle, gift, and trade affecting multiple histories through one exact-head `world.planTransaction` and `executeTransaction` operation.
8. Rebuild factual memory through `subjects.memory.project` and require admitted event citations. Retain AI summaries only as rebuildable projections.
9. Use `receiz.bearer.*` for subject ownership transfer. Define recipient mode, acceptance, expiry, inventory disposition, prior-owner conversation policy, and pending custody explicitly; require former-owner revocation and new-owner reauthorization.
10. Replace broad ownership-derived application access with the narrow v120 subject, Twin, memory, mandate, world, runtime, relationship, and inventory scopes.
11. Upgrade agent integrations to the exact 37 living-subject MCP tools and seven living-subject AI Skills. Confirm stored plan/permit/instrument digests for writes; never send caller-shaped authority JSON.
12. Preserve replay cursors, causal parents, duplicate tolerance, partitions, and forks. Remove every latest-snapshot-wins reconciliation path.
13. For a composite Showcase, carry the exact admitted count and head in the sealed composite proof object, append one successor per new object, and stop automatically rediscovering history already held by that object.

## Verification before activation

Run the coordinated identity lock, SDK/MCP package tests, AI Skills validation, 19-check living-subject conformance, profile/Twin/narration contracts, optimized build, full release freeze, governance checks, and visual evidence on the same frozen candidate.

For transferred or imported subjects, additionally prove exact identity/genesis continuity, prior-head binding, public/private memory policy, unknown-namespace equality, former-owner revocation, queued-job cancellation, and independent replay to the accepted head.

## Rollback boundary

Rollback restores the last exact v120 application/runtime deployment and its durable projections. It never rewrites or removes proof objects, subject events, receipts, ownership transitions, or other admitted history. If a projection is wrong, rebuild it from the accepted exact head. If a transition was never admitted, retry only with the same idempotency identity or create a new explicit attempt according to the returned failure.
