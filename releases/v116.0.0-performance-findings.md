# Receiz v116.0.0 Performance Findings

@receiz/sdk preserves durable proof memory: first admission only, then append
forever.

## Known-Proof First Paint

Accepted PBI identity proof remains visible when an owner leaves and returns.
Known verified local truth paints before server, session, database, or unsigned
owner projection. Refresh may append stronger verified additions; it cannot
erase, blank, or remount the accepted proof as generic loading state.

This release promotes the proven baseline. It does not add an orchestration
layer or move known-proof projection behind new network work.

## Checkout And Credit Reconciliation

Hosted checkout return reconciles paid credit truth before presenting a final
balance. Purchased credits remain non-expiring and follow the complete
settlement lifecycle:

- checkout admission
- refund reversal
- payment-dispute loss debit
- idempotent dispute-win restoration

Repeated lifecycle delivery cannot duplicate a debit or restoration. A stale
route-local balance is weaker than accepted settlement state.

## Creator Execution

Active signed subscription terms reach Business Creator execution. Carrying
the already accepted term is bounded context propagation; rediscovering or
reconstructing entitlement separately on each metered route is not authority.

## First-Use Path

First use begins with Composer and four direct steps: establish the proof place,
create the first post, add a cover, and copy the link. Optional Twin setup is
not added to first-paint or publication prerequisites.

## Qualification Boundary

The upstream candidate records that an incomplete offline install removed its
dependency tree. Therefore the upstream focused, lint/build, release-freeze,
governance, attestation, and visual gates remain unchecked in this release
book.

The standalone verifier's configured static gates may pass independently.
They qualify only this distribution and cannot substitute for the missing
upstream dependency tree or product evidence.

## Release-Lock Requirement

`pnpm release:lock 116.0.0` must require this record. A future change cannot
delay known proof for refresh, present stale checkout credit truth, duplicate
dispute reconciliation, drop signed execution terms, or put optional Twin
setup before the first useful act.
