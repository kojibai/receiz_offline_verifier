# Receiz v119.0.0 Regression Lessons

Developer surface: `@receiz/sdk@119.0.0`. Durable proof-memory law: first admission only, then append forever.

## What Regressed

## The regression

Sports already retained hundreds of events correctly, but later code restored
claims, append rows, exact registry cards, and event proofs through separate
effects. The visible result could paint a base/default player rate, zero or
partial score, and a partial history count, then hydrate to truth already held
on the device.

The same structural error appeared elsewhere as a lower identity-seal count or
partial profile/card history painting before a later refresh. The proof objects
were durable; the first projector stopped honoring their active head.

## Why It Regressed

- React state initialized to empty even when verified local truth existed.
- Arrival order was allowed to behave like authority in merge helpers.
- Current rate/value were reconstructed from weaker registry discovery instead
  of being appended into the card proof state.
- Active projection stores overwrote keys without a separate immutable artifact
  store.
- Count equality was used as a shortcut for exact proof lineage.
- Dense hydration arrays were allowed to stand in for recursive head state.

## The correction

- Initial state reads the verified first-paint handoff and held append head.
- Card rate, projected score, live score, value, and history count are one
  higher-Kai state projection beneath the enclosing card proof object.
- Asset and artifact admission compare Kai and exact lineage; stale/equal
  conflicts cannot overwrite held truth.
- IndexedDB stores immutable sports artifacts separately from active pointers.
- Saved card proof objects also use append-only immutable storage.
- Service-worker activation remains outside user proof databases.
- Registry responses are digest-checked discovery and only changed values
  create a successor.
- Fibonacci ancestry is reused from the admitted append proof and generated by
  the recursive carrier with external checkpoint resolution; it is never
  approximated by a generic bounded list.

## Permanent gates

The V119 release must fail if code reintroduces an empty sports first-paint
append seed, arrival-order head replacement, stale card bytes, mutable-only
artifact storage, PWA proof deletion, base-rate hydration, partial-history
hydration, count-only readiness, or candidate-owned Fibonacci ancestry.

## The Offline Note boundary that remained open

Offline Notes already carried value, identity, Kai order, provenance,
verification, local transfer history, and deterministic fork evidence. That
made competing branches detectable and conservable when their histories met.
It did not by itself stop a restorable software position from emitting a
second candidate before any external witness could observe the first.

Several proposed fixes added more identity, account, receiver naming, server
publication, debt, punishment, or reconciliation. Those were weaker layers
and did not remove the transition duplication boundary. A Receiving Seal could
bind a successor to a named person or installation, but identity did not make
the predecessor's Send authority single-use.

## The Offline Note correction

V119 removes everything from the mandatory Cash Send path except the conditions
that prevent a second authorized successor:

```text
exact current head
+ qualified irreversible custody
+ atomic one-use consumption
+ one anonymous qualified next-custody commitment
+ whole-value canonical successor
```

The sender cannot release successor bytes before the exact custody position is
consumed. The receiver cannot activate copied bytes in arbitrary installations
because the successor names one qualified next-custody commitment. The next
holder repeats the same law. Identity remains optional policy, and server
publication remains optional distribution.

Qualification fails closed because a browser-reported flag or counter is not
physical rollback evidence. Every installation is attempted automatically, but
the transferable path opens only when the platform supplies vendor/platform
attestation, single-device non-backup state, user verification, an advancing
strict counter, and the executable rollback-conformance sequence bound to the
exact custody key, RP ID, origin, and state head. An environment that cannot
supply that proof still verifies Notes and uses connected Send; no value moves
into weaker offline custody.

Genesis follows the same authority-removal law. The Reserve source is the
verified `receiz.account.state.v3` portable state carried by the Receiz
Key/Identity proof. The external funded event must first be sealed against that
exact account predecessor and a preselected qualified Reserve-custody
commitment; legacy or unbound Reserve cannot authorize Offline Note issuance.
Local issuance composes and canonical-verifies the
Reserve-debit account successor and equal whole-value held-bound Note genesis,
then activates that exact Note in qualified custody. A Supabase RPC, server
commit, database row, session, or network response is optional later projection;
none may gate or release the Note, authorize issuance, establish Settlement, or
replace the carried Reserve proof.

## Permanent Offline Note gates

The V119 release must fail if an unqualified installation can create or send a
transferable Offline Note; if a caller-shaped qualification, profile label,
account, username, Receiz ID, PBI, server, or database can replace custody
proof; if one consumed head can emit another authorized successor; if value is
not preserved whole; if receiver binding is not exact; if receiver activation
does not verify the enclosing successor first; or if later publication is
described as completing local Settlement. It must also fail if genesis does not
start from the exact verified `receiz.account.state.v3` Reserve head, if the
Reserve-debit and held-bound Note successors do not verify together at equal
value, or if any server-side operation gates or releases local issuance.

## Locked Rules

Known verified truth paints first. Arrival order never selects a causal head.
Offline Note creation and Send require exact qualified irreversible custody,
whole-value conservation, canonical verification, and one-use predecessor
consumption. Server, database, session, identity naming, and publication remain
subordinate.

## Contract Gates

The release lock, deterministic-surface and first-paint contracts, canonical
artifact and primitive-binding suites, Offline Note custody corpus, coordinated
package identity, Academy archive validation, governance checks, build, and
full release freeze enforce these rules.
