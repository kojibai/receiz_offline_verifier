# Receiz v122.0.0 Release Process

The proof object is authority throughout the release.

## Goal

Ship the v122 SDK, MCP, AI skill, and production developer API surfaces as one coordinated proof-native release without changing the settled Receiz application experience.

## What Worked

1. Generate the v122 registry and coordinated SDK/MCP/AI projections.
2. Run focused v122 contracts, package tests/typechecks, settled-application non-regression gates, and the full release freeze.
3. Run governance checks, emit and verify the attestation, then inspect/install package tarballs.
4. Prove the production database target, apply the migration, deploy the exact attested commit, and run security/private-data/first-paint smoke checks.
5. Publish the three coordinated packages, verify clean installation, then tag the exact commit `v122.0.0`.

## What Did Not Work

Partial package checks were insufficient to prove repository-wide release readiness. Historical fixture materialization, current-version documentation, lint, service-worker release identity, production authority composition, and the full release freeze must all be checked from the final commit.

## Practical Rule For Future Work

Advance registry, SDK, MCP, skills, production routes, migration, release evidence, and package artifacts together; then run exact outcome, privacy, authority, settled-application non-regression, and full release gates before any external mutation.

Unknown production credentials, deployment identity, migration state, npm publication, or tag state remains explicitly incomplete.

`@receiz/sdk` release evidence preserves first admission only, then append forever.
